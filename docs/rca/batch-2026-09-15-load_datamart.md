# RCA: batch-2026-09-15-load_datamart — 수동 force 재실행으로 같은 기준일 이중 적재

## 요약

- **무엇이**: 배치 기준일 2026-09-15 의 `load_datamart` 가 두 번 성공해(`rows=184532` × 2) `dm.daily_submission_fact` 09-15 분이 `369064` 건으로 이중 적재됐고, 하류 `build_report_cache` 가 그 2배 입력으로 돌았다.
- **언제**: 2026-09-16 02:00:03(첫 실행 START) ~ 03:15:31(두 번째 실행 SUCCESS) KST. 하류 집계는 03:30:01 ~ 03:33:42.
- **원인**: 첫 실행이 평소보다 느리게(25% 도달 576초, 평소 약 231초) 진행되는 중 02:45 SLA 알림(`last_status=RUNNING`)을 받고 "멈춘 것으로 보고" `force=true` 수동 재실행을 했다. 재실행은 살아 있는 첫 실행의 lock 을 무시했고, 두 실행 모두 `mode=append` 로 같은 기준일을 적재했다.
- **확신**: 이중 적재 메커니즘 — 높음(건수가 정확히 2배, 두 실행의 SUCCESS · append 모드가 로그에 있음). 첫 실행이 느렸던 이유(계기) — 낮음(로그에 사유 없음).
- **조치 방향**: 적재를 기준일 단위로 멱등하게(사전 삭제 또는 upsert), `--force` 는 기존 실행의 생존 여부를 확인한 뒤에만 허용, SLA 알림 문구에 진행률을 함께 표시.

### 판정

- **H1 · H2 · H3 채택** — 이중 적재의 메커니즘. 확신도 **높음**: 건수가 정확히 2배이고, 재실행 사유 · lock 무시 · append 모드가 모두 로그 줄로 남아 있다.
- 코드 · 설정 대조: 이 저장소에는 배치 러너 소스가 없다. 팀 파이프라인 규칙 템플릿 `templates/CLAUDE.data-pipeline.md:56` 은 "모든 job 은 재실행 가능(idempotent)해야 한다. 같은 날짜로 두 번 돌려도 건수가 두 배가 되지 않게 upsert 또는 사전 삭제를 쓴다" 고 적고 있어, `mode=append` 동작(`:22`, `:33`)은 이 규칙과 어긋난다. 실제 운영 러너 설정에 같은 규칙이 있는지는 확인 불가.
- **계기(run1 이 왜 느렸나)** — 확신도 **낮음**. H4 · H6 은 기각, H5 는 판단 불가. 로그로 알 수 있는 사실은 run1 이 첫 진행률부터 2.5배 느렸고(`:24`), 직전 상류가 원천 복제 지연 경고(`:19`)와 함께 늦게 끝났다(`:20`)는 것뿐이다.

## 4. 원인

- **직접 원인**: 진행 중이던 run1 위에 `force=true` 재실행(`:30`)이 lock 을 무시하고(`:31` · `:32`) 같은 기준일을 `mode=append` 로 한 번 더 적재(`:33` · `:42`) → `datamart-counts.csv:39` 369064.
- **배경 원인**:
  - 적재가 기준일 단위로 멱등하지 않다(`:22` · `:33` append). 재실행 한 번이 곧 이중 적재다.
  - `--force` 가 lock 소유 실행의 생존 여부(pid · 최근 진행률)를 보지 않는다(`:31`).
  - SLA 알림이 "미완료"만 알리고 진행률은 알리지 않는다 — `:28` 에는 `last_status=RUNNING` 만 있고 직전 진행률(51%)은 없다. 운영자는 이를 멈춤으로 읽었다(`:30`).
  - run1 이 처음부터 느렸다(`:24`, 원인 확인 필요).
- **악화 요인**:
  - 하류 `build_report_cache` 가 입력 불일치를 경고(`:45`)하고도 그대로 집계해 2배 입력을 리포트 캐시에 반영했다(`:46`).
  - DQ 점검은 07:00 에야 이상을 알렸다(`:47`, 구간 밖). 이중 적재 확정(03:15:31) 뒤 약 3시간 45분.
  - run2 의 lock 해제가 생략됐다(`:43`). 이번에는 run1 이 먼저 해제(`:41`)해서 남은 영향은 로그로 확인 불가.

## 6. 수정안(제안만 — 이번에 고친 것 없음)

1. `load_datamart` 적재를 기준일 단위로 멱등하게 바꾼다: 같은 `date` 의 기존 행을 지우고 넣거나(사전 삭제), 키 기준 upsert. 근거 규칙 `templates/CLAUDE.data-pipeline.md:56`.
2. `batchctl` 의 `--force` 는 lock 소유 pid 가 살아 있고 최근 N분 안에 진행률 줄이 있으면 거부하고, "진행 중(64%, 2분 전 갱신)" 같은 상태를 보여 준다.
3. 재실행이 실제로 필요할 때는 기존 실행을 먼저 종료 확인한 뒤 시작하도록 순서를 강제한다(동시 실행 금지).
4. SLA 알림 본문에 직전 진행률 · 마지막 진행률 갱신 시각을 넣어 "느림"과 "멈춤"을 구분하게 한다.
5. 하류 `build_report_cache` 는 `:45` 같은 입력 불일치 경고 시 실패 처리(또는 보류)해 이상 입력을 리포트 캐시에 반영하지 않는다.
6. 이번 건 정리(제안): 09-15 `dm.daily_submission_fact` 중복 행 정리 후 `build_report_cache` 09-15 재계산 — 실행 여부 · 방법은 데이터 담당 확인 필요.

## 7. 재발 방지

- 운영 절차: "SLA 알림 = 재실행" 이 아니라 "진행률 확인 → 멈춤 확인 → 기존 실행 종료 → 재실행" 순서를 런북에 둔다.
- `force` 재실행은 2인 확인(요청자 + 승인자) 기록을 남긴다(이번 로그에는 요청자만 있음, `:30`).
- 같은 기준일 같은 job 의 SUCCESS 가 2번 이상이면 배치 점검(`/batch-check`)의 "중복 실행"으로 매일 아침 자동 확인한다.
