# 변경 영향도 분석

대상: $ARGUMENTS

- 코드는 고치지 않는다. `legacy/` · `modern/` · `db/` 모두 읽기만 하고, 빌드 · 기동 · DB 접속도 하지 않는다(정적 분석).
- 검색 범위는 저장소 전체다. 단 `node_modules` · `build` · `.gradle` · `dist` · `.git` · gradle wrapper 는 뺀다.
- 모든 항목에 저장소 맨 위 기준 `파일:줄번호` 를 단다. 직접 열어 확인한 줄만 적는다.
- <모듈명>: `legacy/item-bank-php` → `item-bank`, `legacy/assignment-thymeleaf` → `assignment`, `legacy/grade-mssql` → `grade`

## 절차

1. **정의 위치.** 대상의 정의를 `grep -n` 으로 찾는다. 같은 이름의 정의가 여러 곳이면(사본 · 오버로드 · 다른 모듈) 모두 적고, 실제로 실행되는 쪽을 근거와 함께 밝힌다.
2. **호출부 역추적.** 직접 호출 → 그 호출부를 부르는 곳 → 진입점(URL 매핑 · 화면 · 스케줄러 · main)에 닿을 때까지 한 단계씩 올라간다.
   - 이름은 코드 호출뿐 아니라 **문자열 속**(SQL 의 `EXEC` · `CALL`, 템플릿, 설정, 스크립트)에서도 찾는다.
   - 단계마다 "A → B" 의 근거는 A 의 몸통에서 B 를 부르는 줄이다.
3. **테이블.** 대상이 읽고 쓰는 테이블 · 컬럼을 줄번호와 함께 적는다. 그다음 같은 테이블을 읽거나 쓰는 **다른** 함수 · 프로시저 · 모듈을 찾는다(쓰기 충돌 · 잠금 순서 · 컬럼 의미 변화를 본다).
4. **규칙 연결.** `docs/<모듈명>/BUSINESS-RULES.md` 가 있으면 대상 줄 범위와 근거가 겹치는 규칙 ID 를 연결한다. 없으면 "규칙 문서 없음"이라고 쓴다. 문서의 줄번호가 현재 코드와 맞는지 한 곳 이상 대조한다.
5. **보존 확인 수단.** `characterization/` · 테스트 폴더에서 대상 화면 · URL · 테이블을 다루는 테스트가 있는지 찾는다.
6. **보고.** 아래 출력 형식으로 답하고, 요청이 있으면 `docs/<모듈명>/IMPACT-<대상>.md` 로 저장한다.

## 출력 형식

1. 대상 — 정의 위치, 한 줄 요약
2. 영향받는 화면 · 진입점 목록 — URL · 화면 | 진입 메서드 | 근거
3. 호출 경로 — `진입점 → … → 대상`, 단계마다 근거
4. 영향받는 테이블 — 테이블 | 대상의 읽기/쓰기 줄 | 같은 테이블을 쓰는 다른 코드 줄
5. 관련 규칙 ID — ID | 규칙 요약 | 겹치는 줄
6. 수정 전에 확보할 테스트 케이스 — 입력 조건 | 기대 결과 | 근거 규칙 · 줄. 경계값 · 조건 없음 · 부수효과(쓰기) 케이스를 포함한다.
7. 추적 한계 — 검색으로 확정하지 못한 경로와 이유

## 추적 한계로 따로 적을 것

- 이름이 문자열 조합 · 리플렉션 · 동적 SQL(`EXEC(@sql)`, `sp_executesql`) · 설정값으로 정해지는 호출
- 저장소 밖에서 올 수 있는 호출(DB 잡 · 배치 · 다른 앱 · 운영자가 직접 실행). 저장소 안에 근거가 없으면 "없음을 확인"이 아니라 "저장소 밖 미확인"으로 쓴다.
- DB 권한(`GRANT`)으로 누가 실행할 수 있는지는 알 수 있어도, 실제로 누가 부르는지는 알 수 없다.

## 하지 말 것

- 검색에서 안 나왔다고 "호출하는 곳이 없다"고 단정하지 않는다. 찾은 검색어와 범위를 적는다.
- 호출 방향을 거꾸로 쓰지 않는다.
- 규칙 문서의 내용을 코드 확인 없이 옮기지 않는다. 문서와 코드가 다르면 코드를 따르고 차이를 적는다.
- 테스트 케이스를 코드에 없는 규칙으로 만들지 않는다. 케이스마다 근거 줄을 단다.
