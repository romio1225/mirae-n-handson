# AI 검증루프 v1

v1 · 2회차 (2026-10-06, 에듀테크R&D팀 초안)

오늘 바뀐 점
- 절차마다 담당(사람 / 리뷰 세션 / 만든 세션)을 붙이고, 리뷰 결과를 받은 만든 세션의 "수용 / 반박 / 확인 필요" 분류 단계를 넣었다.
- 판정 기준(6장)의 "충분한가 · 적절한가"를 지우고 `templates/approval-checklist.md` v1 의 [반려] · [경고] 규칙을 따르게 했다.
- 검증 범위는 요청 1건 = 커밋 범위 1개로, 근거 줄번호는 사람이 원본과 대조하도록 정했다.

AI 가 만든 변경분과 외주사 PR 을 머지하기 전에 거치는 절차다. **만든 쪽과 검증하는 쪽을 분리**하고, 판정은 `templates/approval-checklist.md` 의 네 기준으로 한다. 실행 진입점은 `/verify <범위>`(`.claude/skills/verify/SKILL.md`)다.

## 1. 왜 분리하나

만든 세션은 자기 코드를 옹호한다. 같은 컨텍스트 안에서 "잘 됐는지 확인해 주세요"라고 물으면 만든 이유를 다시 설명받을 뿐이다. 검증은 **변경분만 보는 새 컨텍스트**에서 한다.

## 2. 패턴

| 패턴 | 방법 | 쓰는 때 |
|---|---|---|
| 만든 세션 → 리뷰 세션 | 새 터미널에서 Claude Code 를 새로 띄워 diff 만 보게 한다 | 기본. 모든 변경 |
| Claude 생성 → 다른 모델 리뷰 | 새 터미널에서 `claude --model sonnet` 으로 새 세션을 띄워 같은 diff 와 체크리스트를 넘긴다 | 이관 · 외주 PR 은 이 방식을 기본으로 쓴다 |
| 리뷰어 Sub-agent | 읽기 전용 리뷰어를 `.claude/agents/` 에 정의해 두고 위임한다 | 같은 세션 안에서 격리된 컨텍스트로 리뷰할 때(Day 2-4) |

- 리뷰를 다시 돌릴 때는 리뷰 세션을 `/clear` 하거나 새로 띄운다. 이전 리뷰 기억이 남으면 "아까 지적한 것만" 확인한다.
- PR 이 여러 건이면 건마다 `/clear` 한다.

## 3. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 만든 세션 | 구현, 테스트 작성, 리뷰 이슈의 수용 · 반박 · 확인 필요 분류, 수용한 [반려] · 경고 수정 | 자기 변경의 승인 판정 |
| 리뷰 세션 | diff 읽기, 체크리스트 대조, 테스트 실행, 이슈 목록과 판정 | **코드 수정.** 고치기 시작하면 그 순간 "만든 쪽"이 된다 |
| 사람 | 요청 문장 · 검증 범위 확정, 반박 · 확인 필요의 최종 결정, 근거 줄번호 대조, 최종 머지 | 리뷰어의 판정을 읽지 않고 머지 |

## 4. 절차

| 단계 | 담당 | 하는 일 |
|---|---|---|
| 1. 요청 범위 확인 | 사람 → 리뷰 세션 | 사람이 요청 문장 한 줄과 검증 범위를 준다. patch 면 머리말 `Subject:` 가 요청 문장이다. 범위에 요청이 여러 건 섞였으면 리뷰 세션은 판정하지 않고 범위를 좁혀 달라고 묻는다 |
| 2. 변경 파일 목록과 diff 읽기 | 리뷰 세션 | `git diff --stat <범위>`(patch 는 `git apply --stat`)로 목록을 먼저 보고 파일마다 diff 를 읽는다. patch 는 `review/<PR>` 브랜치에서만 적용한다(작업 브랜치에는 적용하지 않는다) |
| 3. 체크리스트 대조 | 리뷰 세션 | `templates/approval-checklist.md` 항목마다 예 / 아니오 / 확인 필요로 답한다 |
| 4. 테스트 실행 | 리뷰 세션 | 체크리스트 1장의 명령 중 바뀐 폴더 것만 실행한다. 통과 · 실패 수와 실패한 테스트 이름만 남긴다. 서버가 꺼져 있으면 실행하지 않고 사람에게 기동을 요청한다 |
| 5. 판정 · 기록 | 리뷰 세션 | [반려] 항목이 하나라도 "아니오"면 반려. 결과를 `docs/verify/` 에 파일로 남긴다 |
| 6. 근거 대조 | 사람 | 이슈 표의 `파일:줄번호` 를 원본과 대조한다. 어긋난 행은 고치고 "(사람 판정)" 표시 |
| 7. 되돌리기 | 만든 세션 + 사람 | 만든 세션은 리포트 파일 경로를 받아 이슈마다 수용 / 반박(근거 `파일:줄번호`) / 확인 필요로 분류한다. 사람이 결정하고, 수용한 [반려] · 경고만 리뷰가 지적한 파일 안에서 고친다. 다른 파일을 고쳐야 하면 먼저 묻는다. 커밋한 뒤 리뷰 세션을 비우고 2번부터 다시 돈다 |

## 5. 출력 형식

```
판정: 승인 | 반려 | 반려(확인 필요)

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 / 확인 필요 | 실행 명령과 통과 · 실패 수 |
| 치명 이슈 0건 | 충족 / 미충족 / 확인 필요 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 / 확인 필요 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 / 확인 필요 | [반려] 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |

확인 필요
| 파일 또는 범위 | 확인할 질문 |
```

- 이슈 한 건은 심각도(치명 / 경고 / 제안) · `파일:줄번호` · 근거 · 수정 방향 네 항목을 모두 채운다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 따로 적는다.
- 리포트에 비밀값으로 보이는 문자열을 옮겨 적지 않는다. 위치만 적는다.

## 6. 판정 기준 (v1)

- 판정 규칙은 `templates/approval-checklist.md` v1 하나만 따른다. [반려] 항목 "아니오" 1건 = 반려, [경고] 항목 "아니오" = 경고 이슈(판정 영향 없음).
- 기준 안에 "확인 필요"가 남으면 그 기준은 충족으로 쓰지 않고 판정은 `반려(확인 필요)` 로 낸다.
- 컨벤션은 팀 `CLAUDE.md` 와 `convention-check` Skill 항목 1~8 을 기준으로 보고, `CLAUDE.md` 에 적힌 예외는 위반으로 세지 않는다.

## 7. 하지 말 것

- 리뷰 세션은 코드를 수정하지 않는다. 보고만 한다.
- 테스트를 실행하지 않고 "통과"라고 쓰지 않는다. 실행할 수 없었으면(서버 꺼짐, 의존성 미설치) 그 사실을 적고 사람에게 기동을 요청한다.
- 요청 범위를 모르는 상태에서 "범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈 0건이 나오면 "경고 · 제안 수준까지 다시 봐 달라"고 한 번 더 요청한다. 0건은 결과일 수도, 안 본 것일 수도 있다.
